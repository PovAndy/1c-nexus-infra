## Обязательные правила

1. `rsv-data:query` нельзя выполнять без явного списка полей.
2. В нативной схеме инструмента использовать `select`, если он поддерживается.
3. В текущем HTTP MCP:RSV Data через `rsvdata_http_mcp_proxy.py` рабочий эквивалент `select` - `fields`.
4. Для фильтрации через текущий прокси использовать массив `filters`, а не одиночный `filter`.
5. Для проверочных запросов задавать малый `limit`, обычно `1`.
6. В `query` текущего HTTP-прокси передавать только `table`, `fields`, `filters`, `limit`; параметр `object` допустим для `describe`/`get_structure`, но запрещен для `query`.
7. Сырой JSON 1С/PostgreSQL больше 20 строк записывать в `temp/raw_data.json` только через shell/Python redirection и обрабатывать локальным Python-скриптом.
8. В чат выводить только итоговую агрегацию или краткую таблицу до 15 строк.
9. Тяжелые логи из `logs/` сначала сжимать через `1s-log-sentinel` или `owl-librarian`.

## Удачный паттерн

1. Найти точное имя объекта через `describe`.
2. Перед запросом структуры вызвать `get_structure`.
3. Выполнить `query` с явным списком полей, фильтром и лимитом.
4. Если ответ превышает 20 строк, сохранить его локально в `temp/raw_data.json` через shell/Python redirection.
5. Локально извлечь только нужные поля через Python `json` или `pandas`.
6. Если нужен UUID, не считать представление `Ссылка` UUID; сопоставлять ссылку через read-only SQL.

Проверенный кейс:

- объект: `Справочник.икЛицевыеСчета`;
- поля: `Ссылка`, `Код`, `Наименование`;
- фильтр: `Код = 10-1-64`;
- лимит: `1`;
- результат: ЛС найден, UUID сопоставлен через read-only SQL;
- оценочная экономия: около `422` токенов против полной строки объекта.

## Неудачные попытки и запреты

- Не использовать `rsv-data:query` без списка полей: это приводит к широкой выгрузке строки.
- Не выводить сырой JSON RSV/PostgreSQL в чат.
- Не полагаться на `Ссылка` из RSV как на UUID: текущий RSV возвращает представление ссылки.
- Не начинать с предполагаемых имен справочников; точное имя нужно брать из `describe`.
- Для текущего прокси не использовать одиночный `filter` как основной формат: в проверке он не дал целевой строки.
- Для текущего прокси `select` был интерпретирован не как рабочая выборка полей; использовать `fields`, пока нативная схема `mcp-rsv-data` не покажет другое.
- Не повторять много авторизационных попыток при `401/500`, чтобы не блокировать пользователя 1С.

## Batching & Silent Write Protocol

Дата внедрения: 2026-06-26.

Цель: сократить число MCP-вызовов и исключить попадание сырых метаданных/JSON в контекст чата и IDE-буфер изменений.

Обязательные правила:

1. Не более 3 последовательных структурных MCP-вызовов (`describe`/`get_structure`) за одну прикладную задачу.
2. На первом шаге получать структуру метаданных пакетом и сохранять ее локально в `temp/metadata_cache.json`.
3. Для сохранения raw JSON/JSONL/TXT использовать только shell/python redirection или локальные Python-скрипты, не `write_file`/`apply_patch`.
4. При наличии актуального `temp/metadata_cache.json` повторно не обращаться в MCP за той же структурой.
5. Связанные выборки данных объединять в пакетный `execute_query`/1C-запрос с `LEFT JOIN` и ручным Join Predicate Pushdown.

Инструмент кэширования:

- путь: `scripts/silent_metadata_cache.py`;
- вход: JSON из `stdin`;
- выход: запись JSON в указанный файл, без вывода исходных данных в `stdout`;
- проверенный файл кэша: `temp/metadata_cache.json`.

Контрольный тест 2026-06-26:

- `tools/list` использован один раз для подтверждения сигнатуры `get_structure`: параметр `object`;
- выполнен один `get_structure` по `Справочник.икУслуги` через `rsvdata_http_mcp_proxy.py`;
- результат передан pipe в `silent_metadata_cache.py`;
- `temp/metadata_cache.json` создан и прошел JSON-валидацию;
- `silent_metadata_cache.py` прошел `py_compile`.

Удачный паттерн:

1. Один раз проверить сигнатуру инструмента через `tools/list`, если она неизвестна.
2. Один раз получить нужную структуру через `get_structure`.
3. Сразу передать ответ в `scripts/silent_metadata_cache.py` и сохранить в `temp/metadata_cache.json`.
4. Все последующие шаги строить по локальному кэшу, без повторного чтения структуры через MCP.

Анти-паттерны:

- серийно выполнять `describe`/`get_structure` более 3 раз за задачу;
- выводить raw JSON RSV/PostgreSQL в чат;
- сохранять raw dumps через IDE-файловые инструменты;
- дробить диагностическую выборку на микро-запросы вместо пакетного запроса;
- повторно читать структуру через MCP при наличии актуального локального кэша.
