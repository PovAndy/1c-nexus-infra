# Контракт prompt-инфраструктуры reasoning-моделей

## Назначение

Контракт задает единый неизменный developer-префикс для `.clinerules`, `.cursorrules`, `AGENTS.md` и `system_prompt.md`. Его цель — исключить дрейф ограничений между IDE и агентами, сохранить cache-friendly порядок сообщений и отделить неизменяемые правила от динамической задачи.

## Статический и динамический контекст

Блок `OMVL_STATIC_PREFIX_V1` находится в начале каждого потребителя и совпадает байт-в-байт. В нем размещены topology, границы безопасности, роли, Definition of Done и контракт формата результата.

После префикса добавляются только изменяемые сведения конкретной задачи: цель, разрешенная область, проверяемые факты, малый diff, результаты инструментов, критерии приемки и требуемый формат. Секреты, raw-данные 1С, персональные данные, большие логи и значения `.env` исключены из обоих слоев.

## Конвенция reasoning-моделей

Статический блок передается первым сообщением роли `developer`. Переменное задание передается следующим изолированным блоком. Промпты не требуют скрытую цепочку рассуждений, саморефлексию, несколько внутренних кандидатов или искусственный reasoning trace. Вместо этого они задают цель, границы полномочий, доказательства, STOP-условия, критерии приемки и формат результата.

Это согласуется с актуальным руководством OpenAI: для GPT-5.6 рекомендуется сохранять стабильные инструкции, не повторять правила, задавать границы автономии и проверять экономический эффект на представительных задачах. Точный cache hit зависит от API, модели и провайдера, поэтому документ не обещает фиксированный процент экономии.

## Актуальные границы данных

- `ServedBase` разрешен только для read-only диагностики через CodexTestBridge; фактический `bridge_url` проверяется перед выводом о данных.
- Семнадцать локальных источников `x1_XX` неизменно read-only.
- Любая запись, SQL DML, `TestAndFix`, проведение документов и изменение конфигурации требуют отдельного разрешения.
- Локальные LLM и порты `8080`, `8081`, `11434` запрещены.

## Адаптивная оценка BSL-кандидатов

Оценщик `scripts/eval_bsl_candidate.py` реализует детерминированный Best-of-N с максимальным размером выборки два только после отклонения первого кандидата. Он не вызывает модели и не передает BSL за пределы рабочей среды.

- **Fast-path:** Candidate 1 проходит `oscript -check`, проверку временных таблиц, правила BSL-линтера и привязку ссылок на метаданные к предоставленным доказательствам. При `Cost = 0` кандидат принимается без дополнительных LLM-вызовов.
- **Fallback-path:** только при `Cost > 0` оркестратор запрашивает ровно две целевые вариации с перечнем локальных нарушений. Оценщик выбирает только вариацию с нулевой наименьшей стоимостью; при равенстве приоритет у первой вариации.
- **Штрафы:** синтаксическая ошибка — `+1000`, неуничтоженная временная таблица — `+500`, запрещенная BSL-конструкция — `+300`, ссылка на метаданные без доказательного anchor — `+100`.
- **STOP:** отсутствие или тайм-аут синтаксического диагностика, отсутствие двух вариаций после отклонения Candidate 1 либо ненулевая стоимость лучшего результата не допускают приемку. Статическая оценка не доказывает исполнение в платформе 1С и не присваивает `[VERIFIED]`.

## Проверка контракта

Команда `scripts/validate_prompt_contracts.py` проверяет:

1. точное совпадение статического блока всех четырех потребителей;
2. наличие обязательных XML-разделов;
3. отсутствие запрещенных CoT-триггеров;
4. достаточный запас объема по локальным лексическим единицам и UTF-8 размеру;
5. наличие developer-конвенции в `system_prompt.md`.

Локальный проект не содержит SDK-токенизатор провайдера, поэтому число токенов конкретной модели не эмулируется. Механическая стабильность и запас размера — контролируемые предпосылки cache-friendly работы; фактические `cached_tokens`, `cache_write_tokens`, latency и стоимость должны измеряться на выбранном внешнем API.

## Изменение версии

Любое изменение блока `OMVL_STATIC_PREFIX_V1` — изменение контракта. Оно допускается только синхронно во всех четырех файлах, с новой версией маркера при смысловом изменении, запуском валидатора, регрессией безопасных задач и обновлением RAG lifecycle. Изменение одного потребителя запрещено.

Git pre-commit использует отдельные state/lock-файлы для автоматического checkpoint. Он не изменяет активную lifecycle-запись другой задачи; это исключает гонку между коммитом инфраструктуры и независимой прикладной работой.

## Ограничения

Этот контракт не заменяет системные инструкции Codex, политики провайдера, реальную проверку доступа к 1С, BSL/Designer validation или read-only Preview. Он также не активирует сам по себе непроверенные внешние маршруты и не дает право на запись в данные.
