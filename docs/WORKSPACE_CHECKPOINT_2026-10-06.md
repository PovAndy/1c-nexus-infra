# Контрольная точка рабочей среды — 2026-10-06

Английская версия: [WORKSPACE_CHECKPOINT_2026-10-06.en.md](WORKSPACE_CHECKPOINT_2026-10-06.en.md).

## Назначение и границы публикации

Документ фиксирует проверенное состояние инфраструктурного слоя `epf1129` на
дату контрольной точки и описывает безопасный повторный pre-flight через Codex.
Это не слепок всего рабочего дерева и не доказательство развёртывания EPF.
Публичная версия содержит только инфраструктурный код, шаблоны и эту
обезличенную документацию. BSL/XML бизнес-исходники, базы, артефакты сборки,
логи, RAG/runtime state, локальный список серверов, реальные `.env` и приватные
адреса в публичный checkpoint не включаются.

## Архитектура и правила работы

- **Codex** координирует работу, сначала определяет активный профиль модели и
  целевой контур, затем выполняет локальный RAG pre-flight и навигацию Graph V2.
- **Graph V2** предоставляет локальную навигацию по исходникам; это индекс,
  а не доказательство выполнения кода.
- **RAG FSM 2.0** хранит проверенные решения и жизненный цикл записей. Перед
  изменением используется поиск, а состояние базы проверяется
  `scripts/kb_manager.py --validate`.
- **OMVL / WAN25** маршрутизирует облачные роли через OpenAI-совместимый
  gateway. В публичном шаблоне допустимы URL и имена моделей, но не ключи.
- **MCP-контуры** обслуживают тестовый мост, RSV Data и навигацию по метаданным.
  Выбор локальной базы и endpoints хранится отдельно от публичных шаблонов.
- **Gate/hooks** блокируют некорректную сдачу и не должны ослабляться ради
  получения PASS. Живые записи, публикация, развёртывание и опасные операции
  требуют отдельного явного разрешения.

Безопасность по умолчанию: чтение и диагностика разрешены в целевых
read-only-контурах; изменения кода считаются непроверенными до тестов; запись в
базу, публикация EPF и обслуживание сервера требуют отдельного подтверждения.
Все 17 исходных контуров `x1_XX` остаются read-only.

## Текущее подтверждённое состояние

Локальный контур `base02` предназначен для read-only-диагностики. Пароли,
локальный реестр баз и адреса хостов хранятся только в защищённой локальной
конфигурации. Не переносите эти значения в prompt, документацию, логи или Git.

| Проверка | Результат контрольной точки | Ограничение |
|---|---|---|
| COM и постоянный запрос | PASS | Только диагностическая проверка |
| Веб-публикация | HTTP 200 для стартовой страницы | Интерактивный вход не проверялся |
| CodexTestBridge | Health, Metadata и read-only query PASS | Не доказывает доступность иных методов |
| RSV Data MCP | Инициализация и константный read-only query PASS | Только проверенный целевой маршрут |
| OData | `$metadata` валиден | EntitySet отсутствует; чтение данных не подтверждено |
| PostgreSQL | Целевая БД подтверждена, транзакция read-only, SELECT разрешён | DML, DDL и администрирование не разрешены |
| 1c-live-index MCP | Свежий процесс выполнил диагностический запрос | Старые MCP-процессы требуют перезапуска |

Общий gate-check: **7/8 PASS**. **GATE 2 остаётся FAIL**: доступ к историческому
deployment-каталогу отклонён SMB-авторизацией. EPF не объявляется развёрнутым;
локальный артефакт не подменяет доказательство на сервере. Reality
Reconciliation — **WARN**: хеш собранного EPF и контрольные поля расходятся с
handover. Это состояние нельзя считать актуальным baseline.

Отдельные автоматические проверки на момент контрольной точки: env contract —
PASS для 8 целей; prompt contract — 16 996 байт у 4 потребителей; Graph V2 —
актуален, 378 файлов; полный набор GATE 6 — 33 теста PASS. Эти результаты
исторические: перед релизом команды ниже запускаются заново. PASS не переносится
между сессиями как доказательство текущего состояния.

Публичный checkpoint намеренно не содержит локальный реестр серверов,
target-specific adapters с внутренними endpoints и локальную wiring-конфигурацию
MCP/hooks. Live-результаты выше отражают проверку исходной рабочей среды; они
не обещают, что каждый контур повторяется из публичного clone без локальной
настройки.

## Настройка через Codex

### 1. Подготовить локальные параметры

Начинайте с `.env.example`. Скопируйте его в игнорируемый локальный файл,
например `.env.openrouter.local`, задайте права `600` и заполните секреты только
локально. Не выводите значения ключей в терминал/чат и не передавайте их в
аргументах CLI. Секреты разных ролей и контуров не смешиваются.

Для единого WAN25 gateway используйте публичный адрес
`https://apiai.wan-2-5.pro/v1`, `WAN25_GATEWAY_ENABLED=1` и локальный
`WAN25_API_KEY`. Значение `0` отключает общий gateway и оставляет отдельные
маршруты ролей. Не запускайте live-smoke, пока пользователь не ввёл ключ и
отдельно не запросил проверку.

### 2. Стартовый read-only prompt

```text
Выполни read-only pre-flight текущей рабочей среды. Сначала по ключевым словам
проверь локальный RAG, затем определи активный профиль модели и целевую базу.
Проверь env contract, Graph V2, prompt contract и доступность требуемых MCP.
Не читай и не печатай секреты; не изменяй файлы, базы или сервисы. Отдели
текущие доказательства от исторических и выведи PASS/WARN/FAIL с командами.
Не утверждай успешное развёртывание без серверного доказательства.
```

### 3. Команды локальной проверки

Из корня проекта и через проектный Python:

```bash
PY=.venv-gemini-bridge/bin/python
$PY scripts/validate_env_contract.py
$PY scripts/workspace_graph_v2_manager.py check --deep
$PY scripts/validate_prompt_contracts.py
$PY scripts/kb_manager.py --validate
$PY scripts/gate_check.py --reverify
```

GATE 2 может остаться заблокированным до исправления прав на deployment-шару.
Не обходите его локальным файлом, не подменяйте target и не ослабляйте gate.
Для изменений формы 1С сначала используйте `form-info`, затем точечный
`form-edit`, после чего структурную валидацию и EPF pipeline. Перед BSL-правкой
изучите целевой модуль и метаданные; не читайте весь `ObjectModule.bsl`.

### 4. Минимальный live-smoke после ввода ключа

```text
Проведи один минимальный live-smoke нужных облачных ролей штатным OMVL runtime
и общим rate limiter. Не показывай ключ, заголовки, полный ответ или приватный
endpoint. Для каждой роли выведи только alias, маршрут и PASS/FAIL. Не повторяй
запрос вручную при 429; соблюдай Retry-After и локальный лимитер.
```

### 5. Git и публикация

Перед фиксацией проверь `git diff --check`, staged diff, секреты и RU/EN-пару
документации. Добавляй только точный allowlist инфраструктурных файлов.
Запрещены `git add .`, `git add -A`, `git commit -a`; не добавляй `src/`, базы,
RAG/runtime данные, логи, собранный EPF и локальные env-файлы. Перед push
сверяй remote SHA и проверяй, что ветка не содержит бизнес-историю.

## Критерии обновления контрольной точки

Обновляйте обе языковые версии одновременно. Укажите дату, доказательства и
ограничения; не копируйте секреты и локальную топологию. Запускайте тесты и
ворота в текущем окружении. Не записывайте статус RAG `success` до фактического
подтверждения. После публикации проверьте SHA remote и содержимое в свежем
clone. Архивные каталоги `Archive`/`archive` исключайте из навигации и аудита.
