# Профиль GPT-6.1 Sol и безопасная очистка workspace

## Модель и контекст

В корневом и проектном Codex явно установлены `model = "gpt-6.1-sol"` и
`model_reasoning_effort = "high"`. Пользовательская глобальная конфигурация
уже выбирала эту модель; проектные значения закрепляют её для новых сессий.

Локальный `models_cache.json` сообщает окно 500000 токенов и эффективную долю
95%: 475000. `model_context_window` не подменяется вручную. В официальной
справке модели указаны API-окно 1050000 и стандартное окно Codex 500k — это
разные границы применения.

Порог сжатия остаётся 160000 токенов роста после переносимого префикса,
`body_after_prefix`; бюджет одного результата инструмента — 1024 токена.
Это рабочие настройки, а не доказанный минимум расходов. Для API вход свыше
272k имеет повышенную цену полного запроса; для подписного Codex указанная
надбавка не применяется. Переносимый префикс переменный, поэтому ростовой
порог не гарантирует фиксированный общий размер входа.

Источники:

- https://developers.openai.com/api/docs/models/gpt-6.1-sol
- https://developers.openai.com/codex/config-reference

## Уменьшение нагрузки Git и IDE

Включён локальный `core.untrackedCache` после успешного filesystem-теста Git.
В `.git/info/exclude` добавлены только `/context/config-dumps/` и
`/temp/tool_logs/`. Выгрузки конфигураций и журналы не удаляются этим правилом;
новые исходники, настройки и документация остаются видимыми Git.
Соответствующие каталоги исключены из наблюдения VS Code и поиска
вложенных Git-репозиториев. Общий `.gitignore` не изменялся.

Начальная инвентаризация нашла 109472 отдельных untracked-файла, включая
91743 файла в `context/config-dumps/`. Поэтому утверждение «829 untracked —
это временные файлы» неверно: 829 было количеством строк сгруппированного
Git status. Очистка не используется для сокрытия незавершённого кода.

Измеренный Git status: до изменений 16.532 с, после 0.8588/0.3673/0.3494 с.
Условия включают прогрев кэша; универсальная гарантия ускорения на 95% из
этого не следует. Содержимое staged-изменений проверено и сохранено.

## Сохранение доказательств

Пусть W — достижимые существующие зависимости активного реестра и явно
закреплённых handover/логов. Обход использует множество посещённых узлов и
допускает циклы; предположение, что граф обязательно ацикличен, не требуется.

\[
C=F_{old,temporary}\setminus(W\cup F_{source}\cup F_{open}),\qquad
\Psi|_W=\mathrm{id}.
\]

Каждый кандидат сначала попадает в архив с SHA-256 manifest. Удаление исходной
копии разрешено только после проверки всего архива и повторного сравнения
inode, времени, размера и хеша файла. Источники, двоичные обработки, lock-файлы,
открытые файлы, молодые результаты, `temp/audit` и `temp/gates` сохраняются.

Идентичность W доказывает сохранение известных файлов, но сама по себе не
доказывает неизменность внешних сервисов или результата всех проверок.
Поэтому выполняется новый реальный прогон ворот. Для согласования с запретом
переписывать старые JSON добавлен `gate_check.py --reverify --evidence-run NAME`.
Он пишет свежий набор в `temp/gates/NAME/`, не меняя исходные доказательства.
Повторное использование имени и небезопасные пути блокируются. Неудачный
CHECK остаётся FAIL; старый PASS его не заменяет.

Точные списки и результаты: `temp/audit/TEMP_SANITATION_PLAN.json`,
`temp/audit/TEMP_SANITATION_REPORT.json`, `temp/audit/SOL_GIT_PERFORMANCE_AFTER.json`.
Архив находится по `archive_path` из отчёта; файлы восстановимы через manifest.

## Перезапуск IDE

Пользователь явно запросил SIGTERM для Extension Host PID 14084. Перед
сигналом проверяются boot ID, PID, время запуска, UID, путь Node и тип
Extension Host. Завершение родителя активного Codex разрывает эту сессию;
поэтому операция запускается отдельным процессом с задержкой после
сохранения отчётов. SIGKILL и остановка других процессов не используются.

Результат: `temp/audit/EXTENSION_HOST_RESTART_RESULT.json`.
Остановка старого процесса не гарантирует RSS нового ≤512 MiB. Ограничение
V8 old-space для filesystem MCP не является лимитом RSS Extension Host.
Отсутствие нового процесса также не считается измеренным низким RSS.

Если сохранение пользовательского кода не позволяет сократить untracked до
10 или runtime-границы не достигнуты, отчёт использует
`PARTIAL_PRESERVED_WORK`. Это отличается от компрометации доказательств.
Фиктивный `CONVERGED_SUCCESS` не записывается.

Внешние модели и блок [28] остаются приостановленными. Базы 1С и EPF не меняются.
